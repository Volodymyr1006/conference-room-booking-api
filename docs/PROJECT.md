# Документація проєкту: бізнес-завдання та технічні рішення

## 1. Бізнес-контекст

Компанія здає в оренду конференц-зали для бізнесу. Потрібен API, через який:

- **клієнти** знаходять вільний зал потрібної місткості, дізнаються вартість і бронюють його;
- **адміністратор** керує залами та послугами і бачить, як іде бізнес.

### Бізнес-завдання та їхнє вирішення

| Бізнес-завдання | Рішення в API |
|---|---|
| Керувати каталогом залів | `POST / PATCH / DELETE /rooms`, окремі методи для додавання і видалення послуг |
| Швидко знайти вільний зал | `GET /rooms/available`: лише вільні зали достатньої місткості, від найменшого (найвигіднішого), одразу з ціною |
| Прозора ціна для клієнта | Відповідь на бронювання містить деталізацію: скільки годин і за яким тарифом рахується, окремо оренда й послуги |
| Дізнатися ціну до бронювання | `POST /bookings/quote` рахує вартість без створення бронювання |
| Не допустити подвійного бронювання | Атомарна перевірка перетину часу в транзакції БД |
| Змінювати ціни без шкоди для клієнтів | Ціна фіксується на момент бронювання. Зміна тарифу залу не змінює вже підтверджені бронювання |
| Дозволити клієнтам передумати | `POST /bookings/{id}/cancel`. Скасування звільняє час, а в звітах враховується частка скасувань |
| Приймати рішення на основі даних | 5 звітів (див. розділ 4) |

## 2. Бізнес-правила та прийняті рішення

Деякі моменти в ТЗ не визначені однозначно. Нижче рішення, які ми прийняли, з поясненням.

| Питання | Рішення | Чому |
|---|---|---|
| Пікові години (12–14) входять у стандартні (9–18). Що діє? | **Пік має пріоритет**: 12–14 рахуються з націнкою 15% | Інакше пікове правило ніколи б не застосовувалось |
| Бронювання зачіпає кілька тарифів | **Ціна рахується частинами** за кожним тарифом | Чесно для клієнта й однозначно. Приклад: 11–13 = 1 год стандарт + 1 год пік |
| Знижки й націнки діють на послуги? | **Ні, лише на оренду залу** | У ТЗ: «знижка 20% на оренду залу» |
| Як рахувати ціну послуг? | **Фіксовано за одне бронювання** | У ТЗ ціна послуг вказана без «за годину» |
| Години роботи | **06:00–23:00** | Для інших годин у ТЗ немає тарифу |
| Крок часу | **30 хвилин** (10:00, 10:30…) | Звично для бронювання залів, не дає створювати «дірки» в розкладі |
| Бронювання через північ | Не підтримується | Зали працюють до 23:00 |
| Бронювання в минулому | Заборонено (пошук у минулому дозволено) | Захист від помилок клієнта |
| Видалення залу з майбутніми бронюваннями | Заборонено (409). Спочатку треба скасувати бронювання | Клієнти не мають прийти в зал, якого «немає» |
| Що відбувається з даними видаленого залу | **М'яке видалення**: зал зникає з API, історія лишається | Звіти за минулі періоди мають бути правильними |
| Бронювання впритул (одне до 14:00, інше з 14:00) | Дозволено | Проміжки вважаються напіввідкритими `[початок, кінець)` |

## 3. Технічні рішення

### Архітектура

Модульна структура: `rooms`, `bookings`, `reports`, `pricing`. Кожен модуль має однакові шари:

```
routes → controller → service → repository → SQLite
```

- **Controller** відповідає лише за HTTP: взяти перевірені дані й віддати відповідь.
- **Service** містить бізнес-правила. Він нічого не знає ні про HTTP, ні про SQL.
- **Repository** містить лише SQL. Щоб перейти на PostgreSQL, достатньо написати нові репозиторії, а сервіси й контролери не зміняться.
- **Pricing** складається з чистих функцій без залежностей, тому розрахунок вартості легко тестувати й змінювати.
- Залежності передаються через конструктори (**Dependency Injection**) і з'єднуються в одному місці: `src/modules/index.js`.

### Принципи «Чистого коду» (Robert C. Martin)

- **Змістовні назви**: `createIfSlotIsFree`, `ensureWithinWorkingHours`, `calculateRentPrice`.
- **Маленькі функції з однією відповідальністю**: наприклад, перевірка часу розбита на `ensureEndIsAfterStart`, `ensureWithinWorkingHours`, `ensureAlignedToStep`.
- **Single Responsibility**: кожен файл і кожен шар мають одну причину для змін.
- **Open/Closed**: тарифна сітка задана як дані (`tariffs.js`). Новий тариф додається без зміни алгоритму.
- **Немає «магічних чисел»**: `WORKING_HOURS`, `BOOKING_STEP_MINUTES`, `MAX_BODY_SIZE` тощо.
- **Помилки через винятки, а не коди повернення**: ієрархія `AppError` → `NotFoundError`, `ConflictError`…
- **DRY**: спільні схеми валідації, презентери, утиліти дат і грошей.
- **Тести** як документація поведінки.

### Безпека

| Загроза | Захист |
|---|---|
| Несанкціонований доступ | API-ключі з ролями `admin` / `client`, порівняння за сталий час (`timingSafeEqual`) |
| Перебір ключів, перевантаження | Rate limiting (100 запитів за хвилину з IP, налаштовується) |
| SQL-ін'єкції | Лише параметризовані запити |
| Некоректні або шкідливі дані | Сувора валідація Zod: типи, діапазони, формати, **відхилення невідомих полів** |
| Великі запити | Ліміт тіла запиту 10 KB |
| Витік внутрішньої інформації | Єдиний обробник помилок: клієнт не бачить stack trace і SQL, `X-Powered-By` вимкнено |
| Атаки через браузер | Helmet (CSP, HSTS, nosniff…), CORS лише для явно дозволених джерел |
| Витік ключів у логи | Заголовок `X-API-Key` маскується в логах |
| Слабка конфігурація | Сервер не запуститься без ключів, з короткими або однаковими ключами |
| Запуск контейнера від root | Dockerfile запускає застосунок від користувача `node` |

### Відмовостійкість і надійність

- **Транзакції**: бронювання, його послуги й деталізація ціни записуються або всі разом, або нічого.
- **`BEGIN IMMEDIATE`** під час бронювання не дає двом паралельним запитам забронювати один і той самий час.
- **Обмеження в БД** (`CHECK`, `UNIQUE`, `FOREIGN KEY`) як останній рубіж цілісності даних навіть при помилці в коді.
- **SQLite у режимі WAL** і `busy_timeout`: стійкість до збоїв під час запису та до конкурентного доступу.
- **Гроші в копійках** (цілі числа), тож немає помилок округлення з плаваючою комою.
- **Коректна зупинка** (graceful shutdown): при SIGTERM сервер завершує поточні запити й закриває БД.
- **`/health`** для моніторингу. Docker `HEALTHCHECK` і `restart: unless-stopped` автоматично перезапускають сервіс.
- **Структуровані логи (Pino)** з `X-Request-Id`, за яким будь-який запит легко знайти в логах.
- **Fail fast**: помилки конфігурації виявляються під час запуску, а не під час першого запиту.

### Масштабованість

- **Версіонування API** (`/api/v1`): нова несумісна версія додається поруч як `/api/v2`.
- **Міграції БД**: зміни схеми додаються новими SQL-файлами.
- **Перехід на PostgreSQL** стосується лише шару репозиторіїв. Для кількох екземплярів сервера за балансувальником це наступний крок, а обмеження частоти запитів можна перенести в Redis.
- **Пагінація** списку бронювань, **індекси** для пошуку перетинів і вибірок за періодом.
- **Модулі** незалежні, тож нові функції (оплата, сповіщення, акаунти клієнтів) додаються окремими модулями.

### Чому саме такі технології

| Технологія | Чому |
|---|---|
| Express 5 | Найпоширеніший фреймворк Node.js, нативна обробка async-помилок |
| SQLite (better-sqlite3) | Не потребує окремого сервера БД (перевіряльник запускає проєкт однією командою), при цьому підтримує справжні транзакції та обмеження |
| Zod | Валідація й перетворення даних в одному місці, зрозумілі повідомлення українською |
| node:test + Supertest | Вбудований тест-раннер Node.js: менше залежностей |
| Swagger UI + OpenAPI 3 | Інтерактивна документація, де можна одразу надсилати запити |

## 4. Звіти для бізнесу

| Звіт | Бізнес-питання | Яке рішення допомагає прийняти |
|---|---|---|
| `summary` | Скільки заробили і скільки бронювань скасовано? | Оцінка виручки, контроль частки скасувань (можна запровадити передоплату) |
| `rooms` | Які зали прибуткові, а які простоюють? | Змінити ціну залу, що простоює, або переобладнати його |
| `services` | Які послуги популярні? | Закупити більше обладнання, створити пакети послуг |
| `tariffs` | Скільки дають ранок, пік і вечір? | Перевірити, чи окуповуються знижки і чи варто змінити націнку |
| `hourly-demand` | Коли найбільший попит? | Планувати персонал і ціноутворення за годинами |

## 5. Можливий розвиток

- Акаунти клієнтів (JWT) і перегляд «моїх бронювань».
- Онлайн-оплата та передоплата для зменшення скасувань.
- Email-сповіщення про бронювання.
- Повторювані бронювання (щотижнева нарада).
- PostgreSQL + Redis для горизонтального масштабування.
